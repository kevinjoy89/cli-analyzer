# 双形态工具分别记录两个版本

## 背景

`Tool.Version` 原本是一个字符串。双形态工具（CLI + 桌面端应用包）出现后，这个字段被两方争抢：CLI 探测拿到的版本、桌面端 `.app/Contents/Info.plist` 里的版本。谁先写入谁就赢，导致：

- 纯桌面端工具（WorkBuddy / ZCode / VS Code）没有 PATH 二进制，`--version` 无从下手，永远显示 `—`
- 双形态工具只显示其中一个版本，另一个被静默丢掉（kimi：CLI 2.1.0 / 桌面 1.0.2，界面只显示 1.0.2）
- 更隐蔽的是：桌面版本兜底填了 `Version` 之后，探测逻辑用 `Version != ""` 判断「已知」，于是**再也不会去探测 CLI 版本**——一个字段同时承担「展示值」和「是否已探测」两个职责，语义被压塌

## 决定

`Tool` 上分成三个字段：

| 字段 | 含义 |
|---|---|
| `CLIVersion` | PATH 二进制探测到的版本（`--version` 或 versioned/brew/pyenv 当前版本）。没有二进制就为空 |
| `DesktopVersion` | 桌面端 `.app` 包 `Info.plist` 里的版本。没有桌面形态就为空 |
| `Version` | 展示兜底：CLI 优先，否则桌面端。保留给只读单一版本的下游 |

探测的跳过条件改为 `CLIVersion != ""`（它才是「CLI 形态是否已知」），不再用 `Version`。

**不判定「哪个更新」**：两个版本各是各自形态的事实，谁新谁旧取决于用户怎么装的，应用不做推断也不给建议。

## Considered Options

- **只留一个字段 + 优先级规则**（已废弃）：无论怎么定优先级都会丢掉一侧信息，且丢失是静默的。
- **三个字段分开记录**（已选）：两个版本都能被展示与比较，`Version` 保留兼容。
- **加 `VersionMismatch` 布尔并高亮告警**（曾实现，后移除）：两个值并排展示时，「是否一致」用户自己就能看出来；再加一层文案与叹号属于噪音。字段仍保留在 JSON 里（供脚本判断），但界面不再使用。

## 后果

- 纯桌面端工具不再声称自己有 CLI 形态（`CLIVersion` 为空，界面只显示桌面版本）。
- 桌面端版本读取走 `platform.AppBundleVersion`，用 `encoding/xml` 事件流扫描 plist——`struct` tag 匹配不上 plist 的 `<key>`/`<string>` 交替结构，这是踩过的坑。
- 探测失败不再永久缓存：缓存键是 `path+size+mtime`，一次并发超时会把空版本钉死到二进制变更为止。现改为失败最多重试 `maxCachedFailures = 3` 次。**这个数字是取舍**：从不响应 `--version` 的工具每次启动会多花一个超时，但换来「偶发失败不会变成永久缺版本」。
- 术语表补了 **Form version（形态版本）**：版本归属于形态，而不是归属于工具。
